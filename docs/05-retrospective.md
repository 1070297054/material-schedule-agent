# 实现复盘

本文描述本次 AI 辅助实现的技术观察，**不是候选人的个人学习经历**。个人收获和实际投入时间须由候选人在亲自运行、修改后补充。

## 最难的设计问题

难点是把“模型有决策空间”与“模型不能越权”同时做清楚。

如果用固定条件分支替模型决定所有动作，就只能证明自动化流程。如果让模型自己决定确认状态或宣称保存成功，又会破坏业务边界。本实现让模型选择查询、补查、保存和结束，代码掌握资料、授权、时段与数据库提交的事实。

第二个难点是确认与幂等同时成立。确认前后应当是同一份草稿，但确认后重放旧请求不能撤销授权。实现使用稳定幂等键、原始要求指纹和不能倒退的确认状态，相关回归测试与实际案例均已补上。

## 实现中形成的认识

- 模型选择动作的能力和工程防护是不同的验证对象。规则测试通过，不能证明模型决策正确；真实 Trace 好看，也不能证明并发去重正确。
- 工具结果必须回到下一次模型调用中。预写决策日志和自动重试不构成 ReAct。
- 查询时段只是一时观察。保存需要在事务内重新验证，不能依靠先前的可用性列表。
- 结束状态也需要校验。无保存证据的 completed 应当被拒绝；达到上限后的已保存草稿必须继续如实展示。
- 离线 Mock 对快速验证流程有价值，但必须显著标明证据边界。
- 实际模型可能更信任结构化的 `retryable` 标记。首轮真实测试中，提示词要求保存失败结束，但工具标记可重试；模型重试后实际保存成功。修复统一了工具错误契约，并由工具层限制本次执行再次写入。原始失败样例仍保留，不能把它改成成功日志。
- 只比较最终 `incomplete` 会混淆正确停止和耗尽预算。评估现在检查先观察到无可用时段、再由模型结束的实际步骤，且有“只重复读取”的反例测试。

## 下一步优先级

1. 在现有真实 DeepSeek 记录基础上扩充未见输入与重复试验，测量多次运行的稳定性；当前单轮验收不能代表所有问题和模型的效果。
2. 候选人亲自做一项业务规则修改，记录问题、取舍、测试变化及个人贡献。
3. 若扩展到多人使用，增加用户身份验证、可审计确认记录、草稿取消/改期和数据库迁移。
4. 若接入真实内容平台，先补充规则来源、审核责任、时间窗口和外部同步机制，再讨论发布权限。

后续按用户要求增加本机网页、HTTP 和双 Agent，仍保留单 Agent 对照；未做线上部署、框架集成或生产级 Runtime。双 Agent 的价值是权限分离和可检查的交接，并未证明它比单 Agent 更准确或更省 Token。

补充认识：评估要验证业务不变量，而不是唯一工具顺序。真实审核 Agent 从素材元数据先观察缺字段、补查后再审核也是合理路径。保留首次误判和修复断言的正反例，避免通过强迫模型照抄固定流程来消除误判。
